# SmartPlanner — پایهٔ برنامه‌ریز شخصی

[![PostgreSQL tests](https://github.com/sepehrebra/smart__planer/actions/workflows/tests.yml/badge.svg)](https://github.com/sepehrebra/smart__planer/actions/workflows/tests.yml)

نسخهٔ ۰٫۵: حساب کاربری، شش ترجیح، مدیریت کارها، **فعالیت‌های تکراری**، برنامه‌ریز روز/هفته و ذخیرهٔ برنامه با تاریخچه و Undo/Redo با FastAPI و PostgreSQL.

مثال: کار «انگلیسی، ۶۰ دقیقه» ذخیره می‌شود و پس از شروع دوباره باقی می‌ماند. هر کاربر فقط کارهای خودش را می‌بیند. تلاش دوبارهٔ همان درخواست کار تکراری نمی‌سازد و ویرایش نسخهٔ قدیمی خطای تعارض می‌دهد.

برنامه‌ریز کارها را در وقت آزاد می‌چیند، کلاس و قفل معتبر را حفظ می‌کند و کارهای جا نشده را با دلیل نشان می‌دهد. پیش‌نمایش را می‌توان در درخواست جدا ذخیره کرد، زمان کار را ویرایش کرد و تغییر را برگرداند یا دوباره اعمال کرد. رابط تقویم و اتصال AI هنوز ساخته نشده‌اند. وضعیت آزمون‌ها در [BUILD_STATUS](docs/BUILD_STATUS.md) ثبت شده است.

مثال تکرار: «هر شنبه و دوشنبه یک ساعت انگلیسی» را یک بار ثبت کنید؛ برای هفتهٔ انتخابی دو کار مستقل ساخته می‌شود. انجام یا حذف شنبه، دوشنبه را تغییر نمی‌دهد. تولید دوباره نوبت اضافی نمی‌سازد. ویرایش الگو فقط روی نوبت‌های هنوز ساخته‌نشده اثر دارد؛ نوبت‌های موجود جداگانه ویرایش می‌شوند. [راهنمای فعالیت‌های تکراری](docs/SmartPlanner_Step_06.md) نمونهٔ کامل درخواست‌ها را دارد.

## سازگاری تعهدهای ثابت — قدم ۹

ذخیره، ویرایش و Undo/Redo اکنون تداخل بلوک‌ها با تعهدهای ثابت فعلی را کنترل می‌کنند. اگر کلاس تازه با برنامهٔ قبلی تداخل پیدا کند، دریافت برنامه `sources.fixed_event_conflicts` و `sources.stale=true` می‌دهد؛ زمان کارها خودکار تغییر نمی‌کند. [قرارداد و محدودیت‌های قدم ۹](docs/SmartPlanner_Step_09.md).

## مثال سادهٔ برنامه‌ریزی

پس از نصب پروژه، این مثال بدون حساب یا پایگاه داده اجرا می‌شود:

```bash
python scripts/demo_schedule.py
```

برای فردا به وقت تهران، انگلیسی ۹ تا ۱۰، دانشگاه ۱۰ تا ۱۴ و ریاضی ۱۴ تا ۱۶ نمایش داده می‌شود. مهلت انگلیسی ساعت ۱۰ است و ریاضی زودتر از ۱۴ شروع نمی‌شود. برای این نمونه استراحت صفر انتخاب شده؛ ریاضی پیوسته است و برای عبور از طول تمرکز ترجیحی هشدار دارد. این مثال برنامه‌ای ذخیره نمی‌کند.

مثال ذخیره و برگشت: کار بدون مهلت محدودکننده از ۹–۱۰ به ۱۱–۱۲ منتقل می‌شود؛ Undo آن را به ۹–۱۰ و Redo به ۱۱–۱۲ برمی‌گرداند. هر حالت ذخیره می‌شود و شمارهٔ نسخه جلو می‌رود تا صفحهٔ قدیمی نتواند تغییر تازه را پاک کند. [راهنمای ذخیره و ویرایش](docs/SmartPlanner_Step_05.md) قرارداد دقیق API را دارد.

## اجرا روی رایانه با Docker

پیش‌نیاز: Python 3.12+ برای ساخت تنظیمات و Docker Desktop/Engine همراه Compose.

```bash
python scripts/init_env.py
docker compose up --build
```

API روی `http://localhost:8000` و راهنمای تعاملی مسیرها روی `http://localhost:8000/docs` است. هنوز صفحهٔ محصول ساخته نشده است. برای درخواست‌های تغییر پس از ورود، مقدار `csrf_token` پاسخ ورود را در هدر `X-CSRF-Token` بفرستید؛ کوکی نشست هم باید همراه درخواست باشد. مستندات Swagger به‌تنهایی این هدر را خودکار اضافه نمی‌کند.

`docker compose down` دادهٔ ذخیره‌شده را نگه می‌دارد. برای حفظ اطلاعات از گزینهٔ `-v` استفاده نکنید. پیکربندی Compose مخصوص توسعه روی localhost است؛ استقرار عمومی مرحلهٔ جداگانه دارد.

## اجرا با PostgreSQL موجود

یک پایگاه توسعهٔ خالی بسازید. سپس در پوشهٔ پروژه:

```bash
python -m venv .venv
```

پس از فعال‌کردن محیط مجازی:

```bash
python -m pip install -e '.[test]'
```

متغیر `DATABASE_URL` را به اتصال پایگاه خود تنظیم کنید. نمونهٔ PowerShell با مقادیر جایگزین:

```powershell
$env:DATABASE_URL = 'postgresql://USER:PASSWORD@localhost:5432/smartplanner'
$env:APP_ORIGIN = 'http://localhost:8000'
python -m smartplanner.migrate
uvicorn smartplanner.api:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log
```

## آزمون‌ها

آزمون مدل‌ها و برنامه‌ریز، بدون پایگاه داده:

```bash
python -m unittest discover -s tests -p test_contracts.py -v
python -m unittest discover -s tests -p test_scheduler.py -v
python -m unittest discover -s tests -p test_recurrence.py -v
```

برای آزمون کامل، یک پایگاه **آزمایشی مستقل** انتخاب کنید. آزمون‌ها حساب و دادهٔ ساختگی اضافه می‌کنند و migration را اعمال می‌کنند.

```powershell
$env:SMARTPLANNER_TEST_DATABASE_URL = 'postgresql://USER:PASSWORD@localhost:5432/smartplanner_test'
$env:SMARTPLANNER_TEST_DB_FLAVOR = 'native'
python scripts/run_tests.py
```

GitHub Actions همین آزمون‌ها را با PostgreSQL 17 اجرا می‌کند؛ سپس پایگاه را دوباره راه می‌اندازد و ماندگاری حساب و کار را بررسی می‌کند.

بررسی راه‌اندازی دوباره، برنامهٔ ذخیره‌شده، مسیر Undo/Redo، رسید درخواست تکراری، الگوی تکرار و نوبت‌های مستقل و حذف‌شده را نیز پوشش می‌دهد. هنگام ارتقا به ۰٫۵، migration شمارهٔ ۴ لازم است؛ اجرای `python -m smartplanner.migrate` نسخه‌های لازم را بدون حذف دادهٔ قبلی اعمال می‌کند. قبل از ارتقای دادهٔ واقعی نسخهٔ پشتیبان بگیرید؛ بازگرداندن خودکار migration ارائه نشده است.

## رفتارهای مهم

- ایجاد کار: `client_request_id` یک UUID است؛ هنگام تکرار همان درخواست تغییر نکند.
- ایجاد جدید 201 می‌دهد؛ تکرار معتبر 200 و همان شناسهٔ کار را برمی‌گرداند.
- `PATCH` به `expected_version` نیاز دارد؛ نسخهٔ قدیمی 409 می‌گیرد.
- حذف به `expected_version` در query نیاز دارد و فعلاً نرم است؛ تلاش قدیمی برای ایجاد دوباره، کار حذف‌شده را زنده نمی‌کند.
- خواندن کارِ کاربر دیگر مثل کار ناموجود 404 می‌دهد.
- تکرار: `POST /api/v1/recurring-activities` الگو را ثبت می‌کند؛ `POST /api/v1/recurring-activities/{id}/occurrences` نوبت‌های ۱ یا ۷ روز را با نسخهٔ الگو می‌سازد/دریافت می‌کند. شناسه‌های کارهای خروجی به برنامه‌ریز داده می‌شوند. ساخت نوبت‌ها صریح است؛ پیش‌نمایش برنامه چیزی ذخیره نمی‌کند.
- توقف/حذف الگو، نوبت‌های قبلاً ساخته‌شده را حذف نمی‌کند. روزانه، روزهای منتخب و هفتگی پشتیبانی می‌شوند؛ تکرار ماهانه یا تعهد با ساعت ثابت هنوز ارائه نمی‌شود.
- `POST /api/v1/schedules/preview` با کارهای حساب فعلی پیش‌نمایش ۱ یا ۷ روزه می‌سازد؛ به کوکی نشست و هدر CSRF نیاز دارد. قرارداد و مثال درخواست در [قدم چهارم](docs/SmartPlanner_Step_04.md) آمده است.
- وقت آزاد باید صریح باشد. برای حفظ چیدمان، بلوک‌های خروجی قبلی را در `previous_blocks` بفرستید. بازچینی کاملاً تازه با حذف بلوک‌های قبلیِ قابل‌جابه‌جایی انجام می‌شود؛ قفل‌ها را نگه دارید.
- زمان‌بندی ابتکاری است؛ پیدا نکردن جا به معنی اثبات ناممکن‌بودن تمام چیدمان‌ها نیست. سقف جست‌وجو و رعایت‌نشدن ترجیحات در پاسخ مشخص می‌شوند.
- ذخیره: `POST /api/v1/schedules`؛ ویرایش: `PUT /api/v1/schedules/{id}`؛ برگشت/اعمال مجدد: `POST` به `/undo` یا `/redo`. هر تغییر شناسهٔ درخواست دارد؛ ویرایش و تاریخچه شمارهٔ نسخهٔ مورد انتظار هم می‌خواهند.
- تا ۲۰ وضعیت برنامه نگه داشته می‌شود. Undo/Redo خود کار یا ترجیحات را تغییر نمی‌دهد؛ منابع تغییرکرده، قفل و کار شروع‌شده می‌توانند برگشت را رد کنند. دریافت برنامه با `sources.stale: true` یعنی اطلاعات مبنای آن عوض شده است.
- دو برنامهٔ ذخیره‌شدهٔ یک کاربر محدودهٔ هم‌پوشان ندارند و یک کار در دو برنامه زمان نمی‌گیرد. برای انتقال به برنامهٔ دیگر ابتدا تخصیص قبلی را بردارید. حذف/آرشیو برنامه هنوز ارائه نمی‌شود.
- زمان‌ها باید اختلاف ساعت مشخص داشته باشند؛ مثلاً `2026-09-20T18:00:00+03:30`.
- پس از ورود، `GET /api/v1/auth/session` توکن CSRF همین نشست را برای تازه‌سازی صفحه برمی‌گرداند.
- رمز خام و توکن خام نشست در پایگاه داده ذخیره نمی‌شوند. خطاهای ورودی، مقدار رمز را بازتاب نمی‌دهند.
- سقف تلاش ورود در این نسخه برای هر پردازش است؛ پیکربندی انتشار، بازیابی رمز، تأیید ایمیل و سیاست حذف قطعی داده هنوز تکمیل نشده‌اند.
